# Invyta

**Create. Invite. Celebrate.**

A digital invitation and event-management platform for the Philippine market — interactive invitation webpages with RSVP, guest management, QR check-in, and analytics, instead of a flat invitation image.

This repo is the frontend prototype originating from Figma Make. The backend is [Supabase](https://supabase.com) — Postgres, Auth, and Row Level Security accessed directly from the React app via `@supabase/supabase-js` (no separate API server).

## Getting started

1. Create a project at [supabase.com](https://supabase.com), then in its dashboard's **SQL Editor**, run [`supabase/schema.sql`](./supabase/schema.sql) once.
2. Copy `.env.local.example` to `.env.local` and fill in your project's URL and anon/public API key (Project Settings → API).
3. (Optional) To enable the "Continue with Google" button, add a Google OAuth provider under Authentication → Providers in the Supabase dashboard. Email/password auth works without this step.

**Already have a project from before these patches?** Instead of re-running `schema.sql`, run these in the SQL Editor, in order: `add-free-plan-limits.sql`, `update-premium-templates.sql`, `add-gallery-styles.sql`, `add-account-deletion.sql`, `add-page-layouts.sql`, `add-section-styles.sql`, `add-payments.sql`.

### Payments (PayMongo, per-event upgrades)

Upgrades run through three Supabase Edge Functions in [`supabase/functions/`](./supabase/functions/) — the browser never sees the PayMongo secret key or decides a price. Using the [Supabase CLI](https://supabase.com/docs/guides/cli):

```bash
supabase login
supabase link --project-ref <your-project-ref>

# Secrets (use PayMongo *test* keys first — sk_test_... / whsk_...)
supabase secrets set PAYMONGO_SECRET_KEY=sk_test_xxx
supabase secrets set APP_URL=https://your-app-domain        # where checkout returns to
supabase secrets set PAYMONGO_PAYMENT_METHODS=gcash,paymaya,card   # optional; only methods enabled on your PayMongo account

supabase functions deploy create-checkout
supabase functions deploy confirm-checkout
supabase functions deploy paymongo-webhook --no-verify-jwt   # PayMongo can't send a Supabase JWT; its signature is checked instead
```

Then register the webhook with PayMongo (dashboard → Developers → Webhooks, or the API) for the event **`checkout_session.payment.paid`** at `https://<your-project-ref>.supabase.co/functions/v1/paymongo-webhook`, and store the signing secret it gives you:

```bash
supabase secrets set PAYMONGO_WEBHOOK_SECRET=whsk_xxx
```

Test with PayMongo's test cards/e-wallet simulator, then swap in live keys (`sk_live_...` and the live webhook's secret) when your PayMongo account is activated. Payments still confirm without the webhook — the `/payment/return` page asks PayMongo directly — but the webhook is what catches payments whose tab was closed before returning.

```bash
pnpm install
pnpm dev       # starts Vite on $PORT (default 8443)
pnpm build     # production build
pnpm format    # oxfmt
```

## Architecture

`src/lib/` holds three Context providers — `auth-context.tsx`, `events-store.tsx`, `guests-store.tsx` — that wrap Supabase queries behind the same `useAuth()`/`useEvents()`/`useGuests()` hook shapes the pages consume, so pages don't touch Supabase directly. `src/lib/supabase-client.ts` is the single client instance, configured from `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`. Security is enforced in Postgres via RLS policies (`supabase/schema.sql`), not in the client — the anon key is safe to ship to the browser by design.

```
src/
├── pages/
│   ├── LandingPage.tsx        marketing site
│   ├── Dashboard.tsx          organizer SaaS shell (sidebar + views)
│   ├── auth/                  Login, Register, ForgotPassword, ResetPassword
│   ├── dashboard/
│   │   ├── CreateEventWizard.tsx
│   │   └── builder/           Invitation Builder (sidebar, content/design panels, live preview)
│   └── public/                guest-facing invitation page
├── components/invitation/     section renderers shared by the builder preview and the public page
├── lib/                       Supabase-backed "stores" (auth, events, guests) + client
├── data/                      static reference data (event categories, templates, theme presets, default invitation)
└── types/models.ts            domain types mirroring the spec's DB architecture

supabase/schema.sql             tables, RLS policies, triggers — run once per project
```

### RLS gotchas hit while building this (worth knowing before touching `src/lib/` or `supabase/schema.sql`)

1. **A plain `exists (select ... from other_table ...)` inside a `WITH CHECK` clause doesn't reliably see rows in the referenced table**, even when the same role can read that row directly outside the policy. `guests`' RSVP-insert policy wraps the check in a `SECURITY DEFINER` function (`event_is_published`) instead — the documented, reliable pattern for "check a condition on a related table" policies.
2. **`.insert(...).select()` (PostgREST's `return=representation`) requires SELECT visibility on the row you just inserted, on top of passing the `WITH CHECK` for the insert itself.** Since `guests`' SELECT policy deliberately restricts reads to the event's owner (real guest-to-guest privacy), an anonymous RSVP submitter can insert a row but can't read it back — asking for one anyway makes Postgres reject the whole insert. `submitRsvp` in `guests-store.tsx` intentionally omits `.select()`.
3. **A blanket `select("*")` on a table with an "owner can see own rows OR anyone can see public rows" policy returns the union of both**, not just the caller's own rows. `events-store.tsx`'s `refresh()` (the owner's dashboard list) explicitly filters `.eq("owner_id", user.id)` rather than relying on RLS alone — otherwise every organizer's dashboard would show every other organizer's *published* events mixed into their own list.
